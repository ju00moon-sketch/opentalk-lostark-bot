# 팔찌 검색 `/팔찌검색` — 설계 (2026-09-07)

사용자 요청: "팔찌검색 옵션 (예: .팔찌검색 특90치90) 이거 커맨드도 만들고싶어". 경매장에서 원하는 전투 특성 값을 넘는 팔찌를 골라 즉시 구매가가 싼 순서로 보고 싶다는 뜻이다. 범위 확인 뒤 "ㅇㅇ 그렇게 가자"로 아래 범위를 승인했다.

**최종 등록 결정(2026-09-07)**: 디스코드는 기본 `/팔찌검색`만 슬래시에 등록하고 `ㅍㅉㄱㅅ`·`.팔찌검색` 채팅 입력을 유지한다. 카톡은 기존 `/`·`.` 명령과 별칭을 유지한다.

## 1. 목표와 비목표

- 목표: `/팔찌검색 특90치90`이 고대 4티어 팔찌 매물 중 특화 90 이상·치명 90 이상인 것을 경매장 즉시 구매가 오름차순으로 최대 10개 보여 준다. 디스코드와 카톡에 같은 내용, 채팅 별칭 `ㅍㅉㄱㅅ`.
- 비목표: 부여 효과 내용(치명타 피해·적에게 주는 피해·무기 공격력 등 % 값)의 표시·필터. 공식 API가 응답에도 넣지 않고 필터도 없어 불가능하며 사용자가 인지했다. 비공식 사이트 연동, 입찰·구매, 다음 쪽 조회, 유물 이하 등급, 3티어.

## 2. 데이터 출처 (조사 2026-09-07, 공식 오픈 API)

- `GET /auctions/options`: 팔찌 카테고리 `200040`(장신구 200000 아래). EtcOptions `2 전투 특성`의 하위 코드 = 치명 15 · 특화 16 · 제압 17 · 신속 18 · 인내 19 · 숙련 20. `4 팔찌 옵션 수량` = 고정 효과 수량 1 · 부여 효과 수량 2. `5 팔찌 특수 효과` 26종(강타 39 · 타격 40 · 앵콜 35 · 이동기 및 기상기 재사용 대기시간 감소 63 등, 수치 범위 없음).
- `POST /auctions/items` 검색 본문: `CategoryCode 200040, ItemTier 4, ItemGrade '고대', EtcOptions [{ FirstOption, SecondOption, MinValue, MaxValue }], Sort 'BUY_PRICE', SortCondition 'ASC', PageNo 1`. 기존 `searchAccessories`의 주석대로 MinValue만 주면 필터가 걸리지 않아 MaxValue를 함께 보낸다(특성은 999). 특수 효과는 Min/Max를 null로 주면 0건이라 수치 범위를 주되, 최대 생명력(11,200~16,800)처럼 큰 값이 있어 상한은 999가 아니라 999,999로 둔다(999는 0건, 999,999는 161건 — 기술 검토 P2-1 반영).
- 응답 `Items[]`(쪽당 10, `TotalCount` 전체 수): `Name, Grade, Tier, Level, GradeQuality, AuctionInfo{BuyPrice, StartPrice, BidStartPrice, BidCount, EndDate, TradeAllowCount}, Options[]`. Options의 `Type`은 `STAT`(특화 91 등 전투 특성), `BRACELET_RANDOM_SLOT`(부여 효과 수량 N), `ARK_PASSIVE`(도약 N), `BRACELET_SPECIAL_EFFECTS`(최대 생명력 등, 값이 있으면 Value) 또는 `ABILITY_ENGRAVE`(이동기 및 기상기 재사용 대기시간 감소 등 — 같은 특수 효과가 이 Type으로 오는 매물이 있어 둘 다 특수 효과로 정리, 기술 검토 P2-2 반영). **툴팁이 없고 부여 효과 내용은 오지 않는다** — "특90치90" 실검색 336건의 상위 10개 모두 `부여 효과 수량 2 · 도약 18 · 특화·치명` 네 항목뿐이었다.
- `EndDate`는 `2026-09-08T14:44:53.803`처럼 시간대 없는 KST 벽시계라 변환 없이 월/일 시:분만 표시한다.
- 요청 1회당 조회 1회. 분당 100회 한도는 다른 명령과 공유하므로 같은 조건은 60초 캐시하고 진행 중인 조회를 공유한다.

## 3. 입력과 출력

입력(`옵션` 문자열 하나, 카톡·채팅은 뒤 토큰 전부):

- 전투 특성 + 최소값: `특90`, `치 90`, `특화90`, `신속 100`. 약자 특·치·신·제·인·숙, 전체 이름도 허용. 띄어쓰기 없이 `특90치90`처럼 이어 써도 된다. 값은 1~999 정수.
- 부여 효과 수량: `부여3` 또는 `3부여`(1~3). 고정 효과 수량: `고정2`(1~2).
- 특수 효과 이름(선택): `강타`, `타격`, `앵콜`, `이동기` 등 §2의 26종. `긴급 수혈`·`최대 생명력`처럼 공백이 든 정식 이름은 그대로 써도 되고(토큰으로 쪼개기 전에 정식 이름만 붙여 둔다 — 기술 검토 P2-3 반영) `긴급수혈`처럼 붙여 써도 된다. 일부 짧은 이름 허용. 값 조건은 두지 않는다.
- 같은 특성을 두 번 적거나 모르는 토큰이 있거나 조건이 하나도 없으면 사용법 안내.

출력(디스코드 임베드 / 카톡 평문, 같은 내용):

```
🔍 팔찌 검색 · 특화 90↑ 치명 90↑
조건에 맞는 매물 336개 · 즉시 구매가 최저 10개

1. 888G · 특화 91 치명 92 · 부여 2 · 도약 18 · 마감 9/8 14:44
2. 899G · 치명 93 특화 92 · 부여 2 · 도약 18 · 마감 9/10 04:31
…
※ 경매장 즉시 구매가 · 고대 4티어 · 부여 효과 내용(치피·적추 등)은 API가 주지 않아 표시하지 못해요
```

- 즉시 구매가가 없는 매물(입찰만)은 `입찰 시작 N G`로 표기한다. 특수 효과가 있으면 `· 강타 5`처럼 덧붙인다.
- 매물 0개: `조건에 맞는 팔찌 매물이 없어요 (특화 90↑ 치명 90↑)`. 조회 실패: `경매장에서 팔찌 매물을 가져오지 못했어요. 잠시 후 다시 시도해 주세요`.
- 카톡 본문은 10줄이라 1,500자 예산 안이며 전체 보기 링크는 필요 없다.

## 4. 구조와 분담

제품 단독 구현(기존 시세 명령 패턴). 외부 응답 해석(옵션 코드·Options 필드)이 있어 기술 교차 검토 대상.

- 신규 `src/bracelet-search.js`: 입력 파서, EtcOptions 변환, 응답 정리, 60초 캐시·진행 중 공유.
- 신규 `src/commands/bracelet-search.js`: `/팔찌검색 옵션`, 양 플랫폼 표시, `createExecute({ search, now })`.
- `src/lostark.js`: `searchBraceletAuction(etcOptions)` 추가(`searchAccessories`와 같은 본문, FirstOption을 항목마다 받음).
- `src/commands/index.js` 등록, `src/text-commands.js` 별칭 `ㅍㅉㄱㅅ`, `help.js`·README·`docs/index.html` 행. 디스코드 슬래시는 기본 58개(기존 기본 57 + 팔찌검색)로 재등록하며, 별칭은 채팅 매처에서만 처리한다.

## 5. 인터페이스 계약

- `parseBraceletQuery(text)` → `{ stats: [{ name, min }], randomSlots: number|null, fixedSlots: number|null, specials: [name] }` 또는 잘못된 입력이면 `null`.
- `queryLabel(query)` → `'특화 90↑ 치명 90↑ · 부여 3'`.
- `toEtcOptions(query)` → API `EtcOptions` 배열(특성 `{2, code, min, 999}`, 부여 `{4, 2, n, n}`, 고정 `{4, 1, n, n}`, 특수 효과 `{5, code, 0, SPECIAL_MAX(999,999)}`).
- `searchBracelets(query, { search, now })` → `{ total, items: [{ price, bidStart, stats: [{ name, value }], randomSlots, leap, specials: [{ name, value }], endsAt }], at }`. 같은 `queryLabel` 60초 캐시, 실패는 캐시하지 않음.
- 명령: `resultTexts(result, query)` → `{ title, summary, lines, note }`; `createExecute({ search, now })`.

## 6. 검증 기준

1. 파서: `특90치90`·`특화 90 치명90 부여3`·`치90 특90`(순서 유지)·`3부여`·빈 문자열·중복 특성·모르는 토큰.
2. EtcOptions 변환 코드·범위.
3. 응답 정리·표시: 고정 자료(실검색 응답 사본)로 줄 형식·요약·푸터·0건 문구·입찰 전용 표기.
4. 명령: 디스코드 임베드·카톡 블록, 사용법 안내, 조회 실패 문구, 60초 캐시(두 번째 호출 미조회)·실패 미캐시.
5. 등록: 디스코드 기본 슬래시 58개에 `/팔찌검색`을 포함하고 `/ㅍㅉㄱㅅ`는 등록하지 않는다. 디스코드 `ㅍㅉㄱㅅ 특90치90`·`.팔찌검색 특90치90`, 카톡 `/팔찌검색`·`.팔찌검색`·`/ㅍㅉㄱㅅ`·`.ㅍㅉㄱㅅ`를 확인한다.
6. 실검색 1회씩 디스코드·카톡 최종 응답, 실패 경로(검색 대역 예외) 1회.

> 아래 검증 기록과 정의 수는 플랫폼·등록 정책 변경 전의 이력이다. 현재 입력·등록 계약은 위 검증 기준과 아래 배포 전제를 따른다.

## 7. 배포 전제·위험·결정

- 디스코드 기본 슬래시 58개로 재등록. 새 환경변수·의존성·폰 변경 없음. 홈페이지는 슬래시 58개·채팅 별칭 지원·카톡 전용 2개로 구분한다.
- 위험: API가 팔찌 특성 이름을 바꾸거나 특수 효과 코드를 추가하면 표에 없는 값은 검색만 안 될 뿐 응답 표시는 이름 그대로 나온다. 특수 효과 상한 999,999는 현재 실수치 기준이며 영구 상한은 아니다. 1G 같은 미끼 매물도 그대로 보인다(경매장 원본).
- 결정: 부여 효과 내용은 표시하지 않고 푸터로 안내(사용자 승인). 고대 4티어 고정. 즉시 구매가 오름차순 고정, 다음 쪽 없음.
