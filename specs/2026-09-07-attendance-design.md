# 카카오톡 전용 방별 출석·출석현황 — 설계 (2026-09-07)

> **개정 2026-09-09 — 이름·양식 변경(사용자 요청, 제품 구현)**: 현황 명령을 `/출석현황`·`.출석현황`으로 바꾸고 옛 `/출석체크현황`·`.출석체크현황`은 단어형 별칭(`text-commands.js` ALIASES)으로 한동안 같은 명령에 연결한다. 출력은 `[출석 현황표]` → 빈 줄 → `▼ 출석 현황 전체보기` → 폭 0 공백(U+200B) 500개 한 줄 → `[N위] 닉네임 | NP` 순위표다. 순위는 기존 정렬(포인트 → 횟수 → 닉네임순)의 연번이며 동점도 연번으로 적는다. 월·오늘 출석 여부·횟수·참여 인원·초기화 안내 줄은 사용자 예시대로 표시하지 않는다(집계·저장은 그대로). 기록이 없는 방은 `[출석 현황표]`와 기존 안내 한 줄만 보낸다. 폭 0 공백은 카톡이 긴 메시지를 접어 "전체보기" 버튼을 보이게 하는 용도이며, 기존 1,500자 전송 예산(원시 길이)에 그대로 포함된다 — 공용 `render.js`는 바꾸지 않는다. 순위가 예산을 넘으면 기존 전체 보기 링크로 이어지고 전체 보기 본문에는 모든 순위가 남는다(교차 검토 P2 반영, 2026-09-09). 닉네임 안의 폭 0 공백은 표시에서 지운다. 디스코드 제외·카톡 61개·재등록 불필요·폰 스크립트 무변경은 그대로다. 실제로 접히는지는 카톡 앱 동작이므로 배포 후 방에서 확인한다. 아래 본문의 `/출석체크현황` 표기와 현황 출력 설명(§ 출력)은 개정 전 계약이다.


사용자 요청: 카톡 출첵의 하루 한 번 제한과 포인트를 방별로 분리하고, 현재 방의 출석 기록을 보는 `/출석체크현황`을 추가한다. 방별 0P 시작을 확정했으며, 매월 1일 한국 시간 00:00에 포인트·출석 횟수·현황 집계를 초기화한다. 기존의 1~3P 무작위 지급과 `.ㅊㅊ`·접두사 없는 `ㅊㅊ` 입력은 유지한다.

**플랫폼 결정(2026-09-07)**: 출첵과 출석체크현황은 카카오톡 전용이다. 디스코드 슬래시·텍스트 목록에서는 제외한다. 디스코드 기본 정의 58개는 유지하며 카톡 기본 명령은 61개다.

## 1. 목표와 비목표

- 목표: 카카오톡 `/출첵`·`ㅊㅊ`·`.ㅊㅊ`로 방마다 하루 한 번(한국 시간 자정 기준) 1~3P를 무작위로 받고, 해당 방의 이번 달 포인트와 출석 횟수를 본다. 같은 방에서 같은 날 다시 하면 이미 출석했다고 안내하며, 다른 방에서는 별도로 출석할 수 있다.
- 목표: `/출석체크현황`·`.출석체크현황`으로 이번 달에 현재 방에서 출석한 참여자의 월별 포인트·출석 횟수·오늘 출석 여부를 확인한다. 매월 1일 한국 시간 00:00부터 새달로 집계한다.
- 비목표: 전체 방 멤버 목록·미참여자 명단, 방을 합친 포인트 순위, 포인트 교환·차감·관리자 조정, 연속 출석 보너스, 디스코드와 카톡 계정 통합, 자정 알림.

## 2. 규칙과 저장

- 하루 기준: 한국 시간(UTC+9) 달력 날짜. 23:59에 출석하고 00:00에 다시 출석할 수 있다.
- 월 기준: 매월 1일 한국 시간 00:00에 포인트·출석 횟수·현황 집계를 초기화한다. `last`의 `YYYY-MM`이 현재 KST 달과 같은 기록만 이번 달 기록으로 센다. v2에 별도의 월 필드는 추가하지 않는다.
- 월 전환: 전월 기록은 이번 달 현황에서 제외하며, 해당 사용자의 이번 달 첫 출석은 기존 포인트·횟수를 이어받지 않고 1~3P·1회로 저장한다. 타이머로 파일이나 전월 기록을 삭제하지 않는다. 봇이 꺼진 동안 1일이 지났더라도 다음 요청부터 현재 달을 적용하며, 현황 조회만으로 파일·백업을 변경하지 않는다.
- 포인트: 출석마다 1·2·3 중 하나를 같은 확률로 준다(`Math.random`, 테스트는 주입).
- 방 식별: 폰 브리지가 이미 전달하는 `roomName`을 출석 범위로 쓴다. 방 이름이 같으면 기록을 공유하고, 방 이름이 바뀌면 새로운 범위가 된다. 현 브리지는 고유 방 ID와 전체 방 멤버 목록을 제공하지 않는다.
- 사용자 식별: 카톡 브리지가 넘기는 기존 `kakao:oc:<닉>`을 유지하고, 출석 저장소 안에서만 방별로 나눈다. 등록 저장소 `user-links.json`·한마디 저장소와 공용 `user.id`는 바꾸지 않는다. 카톡 닉을 바꾸면 새 참여자로 센다(기존 브리지 제약).
- 저장: 루트 `attendance.json`에 아래 v2 구조를 사용한다. `json-store.js`의 `readJson`(깨진 파일이면 저장 거부)·`writeJsonAtomic`(임시 파일 → 교체, .bak, 0600)을 유지한다. 배포가 `src/`만 교체해도 기록을 보존하며 기존 gitignore를 유지한다.
- 이전 기록 처리 결정: 사용자 확인에 따라 방별 기록은 0P부터 시작한다. 기존 flat 기록에는 방 정보가 없어 특정 방으로 옮기지 않으며, 원래 내용을 `legacy`에 보관한다. 기존 flat 기록을 삭제하거나 여러 방에 복제하지 않는다. 월이 바뀌어도 `legacy` 보관 내용은 유지한다.
- 변환 시점: 조회는 파일을 생성하거나 변환·백업을 저장하지 않는다. 기존 flat 기록은 메모리에서 해석하며, 첫 성공 출첵에서만 방 기록과 함께 v2로 저장한다.
- 동시성: 읽기·판정·쓰기가 한 동기 구간이라 같은 프로세스에서 겹치지 않는다. 출석 명령의 진행 중 요청도 방별로 구분해 다른 방의 결과를 공유하지 않는다. 파일이 깨져 있으면 저장하지 않고 실패 문구를 낸다.
- 구조 검증: 루트·방 목록·사용자 목록·legacy가 정상 객체인지, 지원하는 버전인지, 각 기록의 `points`·`count`가 0 이상 정수인지와 `last` 날짜 형식을 확인한다. v2 방 기록은 표시 이름 `name`도 검증한다. 손상된 저장소는 `CorruptStoreError`를 던지고 원본·백업을 보존한다. 기존 flat 기록도 같은 수치·날짜 검증을 거친다.

```json
{
  "version": 2,
  "rooms": {
    "방 이름": {
      "kakao:oc:참여자": { "name": "참여자", "points": 2, "count": 1, "last": "2026-09-07" }
    }
  },
  "legacy": {
    "kakao:oc:참여자": { "points": 5, "count": 3, "last": "2026-09-07" }
  }
}
```

## 3. 입력과 출력

- 카톡: `/출첵`, `.출첵`, `/ㅊㅊ`, `.ㅊㅊ`, **접두사 없는 `ㅊㅊ`**. `kakao/handler.js`의 `bareAliases`와 폰 필터가 함께 허용한다. 디스코드에서는 슬래시 `/출첵`·`/ㅊㅊ`를 등록하지 않고 `ㅊㅊ`·`.ㅊㅊ`도 처리하지 않는다.
- 카톡 현황: `/출석체크현황`·`.출석체크현황`. 새 초성 별칭이나 접두사 없는 현황 입력은 추가하지 않는다. 디스코드에서는 실행하지 않는다.
- 출석 성공: `✅ 블레상돈님 출석 완료! +2P · 이번 달 누적 2P · 이번 달 1번째 출석`
- 같은 날 재시도: `블레상돈님은 오늘 이 방에서 이미 출석했어요 · 이번 달 누적 2P · 내일 00:00(한국 시간)부터 다시 할 수 있어요`
- 저장 실패: `출석 기록을 저장하지 못했어요. 잠시 후 다시 시도해 주세요`
- 이름은 카톡 방 닉네임이며 평문 한 줄로 답한다. 별명이 답장에 들어가므로 성공·이미 출석 답장은 `allowedMentions: { parse: [] }`를 유지한다(기술 검토 P2-2 반영).
- 현황 제목은 `📋 방이름 2026년 9월 출석 체크 현황`처럼 현재 방과 `YYYY년 M월`을 표시한다. 둘째 줄은 `2026-09-07 (한국 시간) · 오늘 출석 M명 · 이번 달 참여 N명`이다. 이번 달에 해당 방에서 출석한 사람만 나오며, 출석하지 않은 전체 방 멤버를 추정하지 않는다.
- 현황 행은 닉네임·이번 달 P·이번 달 출석 횟수·오늘 출석 여부를 표시한다. 정렬은 `points` 내림차순 → `count` 내림차순 → 닉네임 한국어순 → 같은 닉네임일 때 사용자 ID순이다. 이번 달 참여자는 `last`가 현재 KST 달인 기록 수, 오늘 출석자는 `last`가 현재 KST 날짜인 기록 수다.
- 이번 달 기록이 없는 방은 이번 달 참여·오늘 출석 모두 0명과 `이번 달 이 방의 출석 기록이 없어요. ㅊㅊ로 첫 출석을 남겨 주세요.`를 표시한다. 말미에는 `매월 1일 00:00(한국 시간)에 포인트·출석 횟수가 초기화돼요.`를 안내한다. 긴 현황은 기존 카톡 전체 보기 경로를 사용한다. 조회 실패나 방 정보 누락은 오류 안내를 보내며 기록을 변경하지 않는다.

## 4. 구조와 분담

기술 역할이 방별 저장·명령 진입점·최종 출력의 통합을 책임진다. 저장 구조·동시성 변경이므로 작성하지 않은 담당자의 교차 검토 대상이다.

- `src/attendance.js`: 방별·월별 `checkIn`·현황 조회·v2 검증과 기존 기록 보관.
- `src/commands/attendance.js`: `/출첵`에 방 이름·표시 이름 전달. 신규 `src/commands/attendance-status.js`: `/출석체크현황`의 조회·문구.
- `src/kakao/interaction.js`·`src/kakao/handler.js`: 방 전달과 브리지 진행 요청의 방별 구분. 다른 명령의 사용자 식별 계약은 유지한다.
- `src/commands/index.js`의 `kakaoCommands`에 현황을 추가한다. 기존 `src/text-commands.js` 별칭 `ㅊㅊ`·`bareAliases`·폰 필터를 유지하며 카톡 도움말·README·홈페이지의 사용법을 맞춘다. 디스코드 기본 명령 58개와 슬래시 등록 내용은 그대로다.

## 5. 인터페이스 계약

- `kstDate(ms)` → `'2026-09-07'`.
- `rollPoints(random = Math.random)` → 1·2·3.
- `checkIn(userId, { roomName, name, now = Date.now, random = Math.random, storePath } = {})` → 성공 `{ status: 'done', gained, total, count, date }`, 같은 방·같은 날 `{ status: 'already', total, count, date }`. `total`·`count`는 현재 KST 달의 포인트·횟수다. 파일이 깨져 있으면 `CorruptStoreError`를 던진다(저장하지 않음).
- `getAttendanceStatus(roomName, { now = Date.now, storePath } = {})` → `{ roomName, date, todayCount, members: [{ userId, name, points, count, last, attendedToday }] }`. `members`에는 이번 달 기록만 위 현황 정렬 순서로 담으며, 조회로 파일·백업을 쓰지 않는다. 월 표시는 `date`에서 구하고 인자·반환 필드는 추가하지 않는다.
- 출첵 명령 `createExecute({ checkIn, now })`, 현황 명령 `createExecute({ getStatus, now })`.

## 6. 검증 기준

1. `kstDate` 자정 경계(14:59:59Z = 23:59:59 KST, 15:00:00Z = 다음 날 00:00 KST).
2. 같은 사용자·같은 날 A방 출석 `done`, A방 재출석 `already`·기록 불변, B방 첫 출석 `done`·별도 누적. 같은 달의 다음 날에는 포인트·횟수를 이어받으며 사용자별 분리와 1~3P 지급도 유지한다.
3. 정상 flat 기록을 조회하면 파일·백업 불변, 첫 성공 출첵 뒤 v2의 `legacy`에 원래 기록 보존·해당 방 0P부터 적립. 손상된 flat/v2와 지원하지 않는 버전은 예외·원본/백업 불변. 저장 예외 시 명령은 실패 문구.
4. 현황은 이번 달 현재 방 참여자만 월별 포인트·횟수·이름순으로 표시하고 이번 달/오늘 인원을 정확히 집계한다. 동점, 자정 경계, 이번 달 기록이 없는 방, 긴 이름과 긴 현황의 전체 보기를 확인한다. 조회로 새 파일이나 백업을 만들지 않는다.
5. 등록: 디스코드 58개 전체 정의 동일, 출첵·출석체크현황과 텍스트 입력 미처리. 카톡 61개 및 기존 출첵 5종 입력, 현황 `/`·`.` 입력을 확인한다. 새 초성 별칭과 폰 변경 없음.
6. 실제 브리지 경로(`handleBridgeMessage`)의 임시 저장소로 A방 `ㅊㅊ` → 성공/재출석, 같은 닉네임의 B방 출석 → 별도 성공, 양쪽 현황·긴 결과 전체 보기까지 확인한다. 같은 닉네임·다른 방의 동시 요청도 결과가 섞이지 않아야 한다.
