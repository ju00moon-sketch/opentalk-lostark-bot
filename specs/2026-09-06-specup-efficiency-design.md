# 스펙업 효율 `/스펙업` — 설계 (2026-09-06)

사용자 요청: "스펙업효율 구현하고 싶다." 평가 기준은 **점수 증가량**(A안, 2026-09-06 결정) — 각 후보를 "올리면 로펙 점수가 얼마나 오르는가"로
평가한다는 뜻이며(현재 상태 체크리스트가 아님), **순위 지표는 그 증가량을 기대 비용으로 나눈 `점수/10만G`**다. 증가량 자체는 각 행에 `(+증가분)`으로
함께 보여 준다. 구현 방식은 **로펙(lopec.kr) 스펙업 가이드의 계산 모듈을 우리 격리 프로세스에서 그대로 실행**하는 것(1안)이다. 성공 기준은 "로펙 스펙업 가이드 표와 같은 항목·같은 점수"이며,
**기대 비용만 공식 경매장·거래소 API의 실시간 시세**로 계산한다(사용자 요청: "경매장 API 활용해서 실시간 검색해서 골드값 효율 따져서").
따라서 점수 열은 로펙과 동일하고, 비용과 `점수/10만G`는 시세 갱신 시차만큼 로펙 표와 다를 수 있다 — 의도된 차이이며 출력에 명시한다.

조사 결과(2026-09-06): 로펙에는 `/character/specupGuide/<닉>` 탭이 있고 표 열은 **종류 · 옵션 · 최종 점수 · 기대 비용 · 점수/10만G**,
하위 탭은 스펙업 추천 / 스펙업 목표 / 강화 최적화, 토글은 페온 제외 · 작열 제외 · 보유 재료 편집이다. 결과는 서버 HTML(RSC payload)에 없고
브라우저가 계산한다. 입력은 우리가 팔찌·아크그리드 효율에 이미 쓰는 `lostarkParser`(장비·악세·어빌리티 스톤·보석·아크패시브·아크그리드·
스킬 포함)와 `POST /api/auction/prices`(시세)이며, `POST /api/specup/shared-enhancement-baseline`도 호출한다(우리 브라우저에서는 400으로 실패해
표가 "계산중"에 머물렀다 — 7절의 확인 항목). 화면 렌더링 코드(청크 6772)에는 표 헤더·토글만 있고 **계산 코드는 페이지 진입 후 동적으로 받는
청크 또는 워커**에 있다.

## 1. 목표와 비목표

목표
- `/스펙업 [닉네임]`으로 로펙 "스펙업 추천" 탭과 같은 항목·같은 점수를 보여 준다. 각 후보의 점수 증가량을 기대 비용으로 나눈 `점수/10만G` 내림차순,
  상위 10개(정렬 세부 규칙은 2절).
- 기대 비용은 공식 API 실시간 시세(5분 캐시)로 계산하고, 우리 API로 값을 못 구하는 항목만 로펙 시세로 보충한다.
- 디스코드 임베드와 카톡 평문 모두 지원(카톡 가독성 규칙: 핵심 수치 위, 항목 사이 빈 줄, 공백 정렬 표 금지, 1,500자 초과분은 전체 보기 링크).

비목표(v1)
- 로펙의 "스펙업 목표"·"강화 최적화" 탭, 보유 재료 편집.
- 페온 제외·작열 제외를 사용자가 바꾸는 옵션 — 로펙 기본값으로 고정한다(기본값은 Phase 0에서 확인).
- 서포터. 로펙이 이 페이지들에 서폿 계산 모듈을 싣지 않으므로(팔찌 효율과 같은 제약) `null` → 실패 문구.
- 자체 점수 시뮬레이션 공식. 로펙 모듈을 대체하지 않는다.

## 2. 사용자 흐름과 출력

명령
- 슬래시 `/스펙업 [닉네임]` (닉네임 생략 시 `/등록` 캐릭터 → 서버 닉네임 폴백, `resolveCharacter` 규칙 그대로)
- 초성 별칭 `ㅅㅍㅇ` (`text-commands.js` ALIASES 한 줄 → 채팅 `ㅅㅍㅇ 닉`, 슬래시 `/ㅅㅍㅇ` 자동 생성)
- 카톡 `/스펙업 닉` · `.스펙업 닉` (매처가 `commands/index.js`를 자동으로 받으므로 추가 작업 없음)
- 옵션 없음. 슬래시 커맨드 수 86 → 88 (`/스펙업`, `/ㅅㅍㅇ`) → 배포 시 재등록 필요.

정렬·개수
- 코어가 준 행은 이미 정렬돼 있다(4절): `per100k` 내림차순, **기대 비용 0G인 행(`per100k: null`)은 맨 앞**(공짜 이득이 어떤 유료 이득보다 앞), 같은 값은
  증가분 내림차순. 명령은 순서를 바꾸지 않고 상위 10개만 표시한다.
- 증가분이 0 이하인 후보는 코어가 이미 뺐으므로 표시 대상에 없다.
- 카톡: **미리보기는 디스코드와 같은 상위 10개**, 전체 보기 페이지(`/p/full/<id>`, 30분)에는 **행 전체**. 둘을 나누기 위해 명령이 카톡 응답에 전체 평문을
  별도 필드로 함께 넘긴다(3절의 브리지 훅). 전체 보기 링크는 **후보가 10개를 넘거나, 본문과 후속 안내를 합친 최종 메시지가 1,500자를 넘으면** 붙인다. 두 조건 모두 아닐 때만 생략한다(예: 짧은 행 8개 → 링크 없음, 긴 행 8개라 한도를 넘으면 링크 있음).

디스코드 임베드(수치는 형태 예시)
```
❙ 블레상돈님의 스펙업 효율
블레이드 (1,775.00) · 현재 로펙 5,115.78

1. 악세 · 반지 2 · 치적 [하]/치피 [중] → 치적 [중]/치피 [중]  5,135.0 (+19.2) · 38,000G · 50.5*
2. 보석 · 겁화 9 → 10 (블레이드 버스트)                      5,128.1 (+12.3) · 45,000G · 27.3
3. 강화 · 완갑 8 → 9 (목표 11)                               5,131.5 (+15.7) · 71,000G · 22.1
…
마지막 열 = 점수/10만G
```
- 한 행 = `순위. 종류 · 옵션  최종점수 (+증가분) · 기대비용G · 점수/10만G`. 증가분 = `finalScore − baseScore`.
- `종류`는 로펙 표 1열 그대로(이번 표본의 실제 값: 악세·강화·보석·카르마·스톤. 각인·상재·아크그리드도 표시 함수에 존재). `옵션`은 로펙 표 2열을 기반으로
  **주대상(부위·번호·스킬명·돌 조합)과 현재 → 다음 행동, 권장 목표가 다음 행동과 다르면 `(목표 N)`**까지 포함해 같은 이름의 행이 구별되게 코어가 조합한다.
- 반올림: 점수·증가분 소수 1자리, 비용은 원값이 소수여도 **천 단위 정수로 반올림**, `점수/10만G` 소수 1자리. 반올림은 명령에서만 한다(코어는 원값).
- 기대 비용 0G 행(진짜 무료 — 4절의 무료 판정을 통과한 행만): 비용 자리에 `무료`, `점수/10만G` 자리에 `—`.
- 푸터 구성(순서 고정): `점수는 로펙 스펙업 가이드와 동일` · `비용은 거래소·경매장 실시간 시세(5분 캐시)` · `시세 기준 HH:MM`(`pricedAt`이 null이면 생략) ·
  `로펙 시세 갱신 지연`(`priceStale`일 때) · `* 로펙 시세`(로펙 시세 행이 있을 때) · `스톤·카르마는 로펙 고정 비용 모델`(`fixed` 행이 있을 때) ·
  `비용 미확인 후보 N개 제외`(`droppedForPrice > 0`). `fixed` 행에는 `*`를 붙이지 않는다.
- 후속 조회 버튼: 기존 `run:커맨드:닉` 규칙으로 `/로펙`·`/팔찌`·`/젬효율`(카톡에서는 "이어서: /로펙 닉 …" 문구로 변환됨).

카톡 평문 — 같은 내용을 한 항목 두 줄로, 항목 사이 빈 줄:

1. 캐릭터 없음: 명령이 코어를 부르기 **전에** 공식 API `getCharacterProfile(닉)`(호출 1회)로 존재를 확인한다. 없으면 기존 `NOT_FOUND_HINT`. 코어는 이 판별을
   하지 않는다(코어의 `null`은 아래 2번으로만 해석).

## 3. 구조와 데이터 흐름

```
/스펙업 닉 ─▶ commands/specup.js ─▶ lopec-sim.getSpecupGuide(닉)  (결과 5분 캐시, 같은 닉 진행 중 요청 공유)
                                        │
                                        ├─ lopec.getSpecPointHtml(닉) ──▶ lostarkParser (5분 캐시, 기존)
                                        ├─ ensureRuntime(html) ──▶ 모듈 묶음 + 진입점 { bangle, arkgrid, specup }  (배포 키 캐시, 기존 확장)
                                        ├─ specup-prices.collect(요구 시세 키) ──▶ 공식 API(경매장·거래소, 전역 5분 캐시) → 부족분 로펙 /api/auction/prices
                                        └─ runInSandbox(script, 'specup', JSON{ parser, prices, options })  (격리: 권한 모델·코드 생성 금지·B안 OS 사용자, 상한 20초)
                                                  │
                                        정규화된 SpecupGuide ◀─┘   ──▶ 명령이 정렬 유지·상위 10개·반올림·임베드/평문 렌더링
```

- **시세 주입(Phase 0 확정)**: 계산 진입 함수(스파이크 시점 이름 `tX(parser, options)`)의 `options`로 넣는다 —
  `enhancementMarketPriceSnapshot: { snapshotId, prices: { [materialId]: G/개 } }`, `auctionPriceSnapshot: { snapshotId, pricesByTarget: { [target]: G/1개(권) } }`,
  `excludeScorchGemUpgrades: true`(함수 기본값은 false라 **반드시 명시**), `excludePeonCost: true`, `peonCrystalPrice95Gold: null`. 재련 `prices`는 **개당** 골드다.
  추천 뷰 함수(`tJ(snapshot, ownedMaterialValues, …)`)의 두 번째 인자는 시세가 아니라 **보유 재료 수량**이므로 전부 "0"으로 둔다(보유 재료 미반영).
- **2단계 평가 — 후보는 로펙 시세로 고정, 비용만 우리 시세로**: 로펙은 효율순 정렬 뒤 `recommendationFamilyKey`별 첫 행을 표시 후보로 고르므로 시세가 표시 대상
  선택에 관여한다. "로펙 표와 같은 후보·같은 점수"를 지키기 위해 ① 로펙 공개 시세(`GET /api/auction/enhancement`, `POST /api/auction/prices`)로 한 번 계산해
  표시 후보의 **식별자 집합을 고정**하고(= 로펙 표), ② 같은 계산을 우리 시세(공식 API 우선, 부족분 로펙)로 다시 돌려 **같은 식별자의 `costValue`만** 가져온다.
  점수는 시세와 무관하므로 두 단계에서 같다. 식별자는 로펙 후보 객체의 고유 필드가 있으면 그것, 없으면 (`recommendationFamilyKey`, 주대상, 현재 → 목표)의 조합.
  ②에서 어떤 식별자를 찾지 못하면 그 후보는 `droppedForPrice`로 뺀다.
- **카톡 미리보기/전체 보기 분리 훅**(기획 담당 수정, 기술 담당 검토): 명령은 카톡 분기(`interaction.platform === 'kakao'`)에서만 payload에 선택 필드
  `kakaoFull`(전체 행 평문)을 싣는다. `render.toKakaoResponse`가 이 필드를 응답에 그대로 실어 주고, `handler.flattenParts`가 `{ body, tail, full }`로 꺼내며,
  `render.fitBridgeMessage(body, tail, { baseUrl, fullTitle, fullText })`는 `fullText`가 있으면 **전체 보기에는 `fullText`를 저장**하고 본문은 기존대로 1,500자에
  맞춘다. 링크 줄은 후보가 10개를 넘어(`fullText !== body`) 본문이 한도 안이어도 붙이고, 후보가 10개 이하라도 최종 메시지가 1,500자를 넘으면 기존 잘라내기 경로로 붙인다 — 2절의 조건과 같다. 필드가 없는 기존 명령은 동작이 바뀌지 않는다(회귀 기준 9절 11항).
  디스코드 분기는 이 필드를 만들지 않으므로 discord.js payload에 영향이 없다.
- **진입점 탐색**: `lopec-sim.js`의 기존 `findEntries`에 `specup`을 추가한다. 초기 `<script>`만으로는 부족하고 웹팩 런타임의 동적 청크 맵에서 추천 코어 청크를
  추가 수집한다. 별도 워커 청크(강화 워커·OCR)는 같은 모듈 ID를 다른 export로 배포하므로 **런타임별 모듈 그래프를 섞지 않는다**(섞으면 초기화 실패). 탐색은 소스
  패턴(`enhancementMarketPriceSnapshot:`을 옵션으로 받는 함수)으로 하고, 본문에 `auctionPriceSnapshot`·`initialRecommendationView`가 있는지 교차 검증한다. 후보가
  0개거나 여러 개면 `null`로 끝낸다(조용히 계산하지 않는다). 계산 자체는 동기 함수라 워커가 필요 없다(Phase 0 확인).

## 4. 인터페이스 계약 — 명령과 코어의 경계

```js
// src/lopec-sim.js (기술 담당)
export function getSpecupGuide(characterName): Promise<SpecupGuide | null>

SpecupGuide = {
  baseScore: number,        // 현재 로펙 점수(반올림 전). 로펙 페이지 표시 점수와 오차 ≤ 0.01
  pricedAt: number|null,    // 이번 비용에 실제로 쓴 **시장 시세**의 기준 시각(epoch ms) 중 가장 오래된 것 — api는 수집 시각, lopec은 snapshotId의 원본 시각
                            // (`multi:` 형식은 포함된 시각 중 최소). 모든 행이 고정 비용(fixed)뿐이면 null
  priceStale: boolean,      // 로펙 시세 응답이 isStale(갱신 지연)인 값을 하나라도 썼으면 true
  droppedForPrice: number,  // 표시 후보 중 비용을 정할 수 없어 rows에서 뺀 개수 — 필요한 시세 키 누락, 비용 모델 없음(예: 아크그리드 젬), 2단계에서 식별자 미발견
  rows: Array<{             // 정렬 완료 · 로펙 기본 필터(작열 제외·페온 제외) 적용 · 로펙 표와 같은 후보 집합 · 증가분 > 0 인 행 전체
    kind: string,           // 로펙 표 1열 "종류" 그대로 (실측 값: 악세·강화·보석·카르마·스톤)
    option: string,         // 주대상(부위·번호·스킬명·돌 조합) + 현재 → 다음 행동 + 권장 목표가 다르면 "(목표 N)" — 같은 이름의 행이 구별되게
    finalScore: number,     // 최종 점수, 반올림 전 (= baseSpecPoint + scoreGain)
    expectedCost: number,   // 로펙 후보의 costValue(골드). 0 이상 유한수, 소수 허용. 표시 문자열 cost(스톤은 "개수")·raw costGold을 쓰지 않는다
    per100k: number|null,   // (finalScore − baseScore) / expectedCost × 100000, 반올림 전. expectedCost가 0이면 null (Phase 0에서 로펙 efficiencyValue와 동일 확인)
    priceSource: 'api' | 'lopec' | 'fixed',  // 'fixed' = 시장 시세를 전혀 쓰지 않은 로펙 고정 비용 모델(스톤 50G/개, 카르마 900G/회).
                            // 시장 시세를 쓴 행은 필요한 키 중 하나라도 로펙 값이면 'lopec', 전부 공식 API면 'api'
  }>,
}
```
규약
- **정렬은 코어가 끝낸다**: `per100k` 내림차순, `per100k === null`(0G) 행은 맨 앞, 같은 값은 증가분(`finalScore − baseScore`) 내림차순. 증가분이 0 이하인
  후보는 넣지 않는다.
- **수치 경계**: `expectedCost`·`finalScore`·`baseScore`는 유한수만. 비용이 `NaN`·음수·무한대로 계산된 후보는 "시세 없음"과 같이 취급해 뺀다(`droppedForPrice`에
  포함). 결과 JSON에 `Infinity`·`NaN`이 들어가지 않는다(JSON에서는 `null`로 변해 의미가 사라지므로 코어가 직렬화 전에 걸러야 한다).
- **무료와 누락의 구분**: 로펙 원본은 시세가 빠진 후보도 `cost="0"`으로 표시하므로 표시 문자열로 무료를 판정하지 않는다. 한 후보가 **무료**인 조건은
  `costValue === 0` **이고** 그 후보가 요구하는 시세 키가 모두 사용한 스냅샷에 있을 때뿐이다. 요구 키가 하나라도 없거나 비용 모델이 없는 후보(아크그리드 젬처럼
  시세 evaluator가 연결되지 않은 그룹)는 무료가 아니라 `droppedForPrice`다.
- **실패는 전부 `null`**: 로펙 미갱신·서포터·진입점 탐색 실패·격리 시간 초과·시세 전체 실패·**후보는 있었으나 시세 누락으로 전부 제외**·결과 크기 초과.
  예외를 명령으로 전파하지 않는다. 로그는 코어가 `console.error('[스펙업] …')`로 남기고, 마지막 경우는 `시세 누락으로 후보 N개 전부 제외`를 적는다.
- **정상 빈 결과와 실패의 구분**: 로펙 모듈이 낸 후보가 0개이면 `{ rows: [], droppedForPrice: 0, … }`(정상 — 명령은 "추천할 스펙업이 없어요"). 후보가 1개 이상인데
  시세 누락으로 `rows`가 비면 `null`(실패). 일부만 빠졌으면 남은 행과 `droppedForPrice > 0`을 준다.
- 반올림·천 단위 표기·상위 N 자르기·카톡 전체 평문 생성은 명령의 책임. 코어는 원값과 전체 행을 준다.
- 계약은 Phase 0 결과로 **한 번** 갱신될 수 있다(예: `per100k` 정의, `kind` 값 목록). 갱신은 이 문서 4절과 인수인계 문서에 함께 적는다.

## 5. 시세 수집 규칙 — `src/specup-prices.js` (기술 담당)

- 입력: 2단계 평가의 ①에서 고정한 표시 후보가 요구하는 시세 키 — 재련 `materialId`(27종 중 필요한 것)와 거래 `target`(`gem.{종류}.{레벨}`, `market.engraving.{각인명}`,
  `accessory.{등급조합}.{옵션키}`). 출력: 계산 모듈에 넣을 두 스냅샷과 메타 — `{ enhancement: { snapshotId, prices }, auction: { snapshotId, pricesByTarget },
  sourceByKey: { [키]: 'api'|'lopec' }, marketAt: ms|null, stale: boolean, apiCalls: number, missing: string[] }`.
- **로펙 시세를 먼저 받는다**(두 경로 모두, 전역 5분 캐시): 강화 재료는 `GET https://lopec.kr/api/auction/enhancement`, 거래 물품은 `POST …/api/auction/prices`
  본문 `{ targets: [...] }`. 이 값이 ①(후보 고정)의 입력이고 ②의 보충값이다. 응답의 `isStale`·`staleReason`은 `snapshot` 바깥 필드라 따로 보존해 `stale`로 올린다.
- **공식 API로 덮어쓴다** — 정확히 매핑되는 키만, 우선순위대로, 예산 안에서:
  1. 보석 `gem.{종류}.{레벨}` → `searchAuctionItems(210000, "N레벨 종류의 보석")`, 양수 `AuctionInfo.BuyPrice`의 최저값(0·null 제외). 작열은 수집 전에 제외.
  2. 각인서 `market.engraving.{각인명}` → `searchMarketItems(40000, 각인명, { grade })`(후보 metadata의 등급), 정확 품명·등급의 권당 현재가.
  3. 재련 재료 → 카테고리 페이지 조회(`50010` 기본 재료, `50020` 보조 재료 — 1페이지가 카테고리 전체가 아니므로 필요한 품목이 다 나올 때까지 페이지 추가),
     단가 = `CurrentMinPrice / BundleCount`, `fragment`는 **운명의 파편 주머니(대)** 기준 `÷ BundleCount ÷ 3000`(효율표의 소주머니 ÷1000 단가와 혼용하지 않는다).
  4. **악세 `accessory.*`는 v1에서 공식 API로 덮지 않는다**(로펙 target에 품질·티어·등급·부위·옵션 배치 정보가 없어 같은 최저가 조건을 재현할 수 없음) — 로펙 값 유지.
  5. 스톤·카르마는 시세 키가 없다(로펙 고정 비용 모델). 페온·크리스탈은 기본 옵션(페온 제외)에서 불필요.
- **예산**: 시세용 공식 API 호출 **≤ 14회** + 명령의 캐릭터 존재 확인 1회 = 캐릭터당 ≤ 15회. 예산에 걸리면 남은 키는 로펙 값을 그대로 쓴다.
- **보충(로펙 값 유지) 사유** — 어느 경우든 `sourceByKey`에 `lopec`으로 남긴다: 공식 API 실패·빈 응답·비양수값 · 매핑 불명(악세 등) · 예산 한도 초과.
  로펙에도 없는 키는 `missing`이고, 그 키를 요구하는 후보는 ②에서 `droppedForPrice`가 된다.
- 캐시: 전역 5분(보석 시세판·효율표와 같은 수명). 캐시가 비었을 때 **캐릭터당 공식 API 호출 ≤ 15회**, 5분 내 재호출 0회. 분당 100회 한도는 운영 봇과
  공유하므로 이 상한을 넘기는 매핑은 병합 요청 전에 줄인다.
- **진행 중 요청 공유**: 조회 묶음 단위(경매장 검색 조건 하나, 거래소 카테고리 조회 하나)로 진행 중 Promise를 보관해, 서로 다른 캐릭터의 동시 요청이 같은
  묶음을 두 번 부르지 않게 한다(보석 시세판이 쓰는 방식). 성공은 5분 캐시에 넣고, **실패는 캐시하지 않고 진행 중 항목만 지워** 다음 요청이 곧바로 재시도한다
  (실패 묶음이 결과에 필요하면 그 회차는 로펙 보충 → 그래도 없으면 해당 후보 제외).
- **시각**: 공식 API 키는 수집 시각, 로펙 키는 `snapshotId`의 원본 시각(`multi:` 형식은 포함된 ISO 시각의 최소, 파싱 실패 시 수집 시각으로 대체하고 `stale`을 true로).
  `marketAt`은 실제로 쓰인 시장 키들의 최소, 시장 키를 하나도 안 썼으면 null. 로그에는 수집 시각·원본 시각·stale을 따로 남긴다.

## 6. 예산·캐시·동시성·안전·관측

- 시간 예산: 디스코드는 `deferReply` 뒤 여유가 충분하다. 카톡 브리지는 총 25초 — 로펙 페이지·시세 API 2회(캐시 미스 ~1초) + 공식 API(캐시 미스 시 병렬 ~3초) +
  격리 계산 **2회**(2단계 평가, Phase 0 로컬 실측 회당 약 1.0~1.1초·최대 RSS 78.5MiB; **회당 상한 20초**, 기존 팔찌·아크그리드는 15초 유지). 운영 서버(1 vCPU·B안
  래퍼)에서의 실측은 통합 검증에서 다시 한다. 초과 시 기존 브리지 경로가 "다시 보내 주세요"와 3분 보류 캐시로 처리한다.
- 로펙 요청 수: 캐릭터 페이지 1 + 시세 2(전역 5분 캐시) — 기존 `/로펙`·`/팔찌`와 같은 수준.
- 캐시(모두 메모리, 재시작 시 만료): 결과 캐릭터당 5분 · 시세 전역 5분 · 로펙 페이지와 모듈 묶음은 기존 5분·배포 키.
- 동시성: 같은 캐릭터 진행 중 요청은 하나의 Promise를 공유한다(보석 시세판과 같은 방식). 격리 프로세스는 **동시 2개 상한**, 초과분은 대기열(서버 1 vCPU).
  대기로 인한 카톡 예산 초과는 위 브리지 경로가 흡수한다.
- 안전: 로펙 코드 실행 격리는 기존 그대로(`--permission`, 파일은 harden만 읽기, 코드 생성 금지, 256MB, `LOPEC_SANDBOX_WRAPPER` B안). 시세는 JSON 직렬화로만
  주입하고 결과 JSON 1MB 상한을 유지한다. 새 환경변수·포트·권한 없음.
- 관측: 계산마다 한 줄 `[스펙업] 닉 · 행 N개 · 격리 X.Xs · 시세 api N/lopec M`. 로펙 보충 비율이 커지면 API 매핑 누락 신호로 본다.

  이 두 파일은 기술 담당이 같은 기간에 만지지 않는다(만져야 하면 먼저 인계). **Phase 1과 병행** — 4절 계약대로 고정 행을 돌려주는
  스텁 `getSpecupGuide`로 먼저 만들고 코어가 오면 스텁만 뺀다.
- 파일 경계: 위 목록의 파일을 양쪽이 겹쳐 만지지 않는다. 계약 변경이 필요하면 코드보다 먼저 이 문서 4절을 고치고 상대에게 인계한다.
- 통합: 통합 책임자가 코어 브랜치를 자기 워크트리에 합쳐 9절의 통합 검증을 한 뒤 인계 블록으로 넘긴다. dev 머지·main 머지(=배포)·재등록·패치노트는 출시 담당.
- 교차 검토: 코어는 기획 담당이 요구사항·회귀 관점으로, 명령·출력은 기술 담당이 검토한다. 받지 않은 검토를 완료로 적지 않는다.

## 9. 검증 기준

코어 인수 조건(기술 담당, 병합 요청 전)
1. 딜러 3명(블레상돈 · 건슬상돈 · 초코상돈): `kind`·`option`·`finalScore`가 같은 시점의 로펙 표와 일치(점수 오차 ≤ 0.01), `baseScore`가 페이지 점수와 일치.
2. 모든 행에서 `per100k`가 확정된 정의와 일치(기대식 기준 오차 ≤ 0.01).
3. 서포터(꿈지향) · 격리 시간 초과(인위적 1ms 상한) · 시세 묶음 전부 실패 → `null`, 예외 전파 없음, 호출 프로세스 생존. (없는 캐릭터는 명령이 먼저 걸러 코어에 오지 않는다.)
4. 캐시가 빈 상태에서 캐릭터 1명 계산 시 **시세용 공식 API 호출 ≤ 14회**(+ 명령의 존재 확인 1회), 5분 안 재호출 0회(호출 카운터로 확인). 우선순위(보석 → 각인서 →
   재련 재료)대로 예산을 쓰고 넘친 키는 `sourceByKey`가 `lopec`.
5. 수치 경계: 진짜 무료 후보(costValue 0 + 요구 키 전부 가용) → `per100k: null`이고 정렬 맨 앞 · `cost="0"`이지만 요구 키가 빠진 후보 → `droppedForPrice` · 비용
   `NaN`/음수/무한대 후보 → 제외되고 집계 · 결과 JSON 문자열에 `Infinity`·`NaN` 부재 · 소수 비용이 원값 그대로 전달 · 스톤·카르마 행은 `priceSource: 'fixed'`이고
   `expectedCost`가 costValue(골드, 스톤의 "개수" 문자열이 아님).
6. 빈 결과 구분: 후보 0개 → `rows: []`(비-null) · 후보 3개 중 비용 미확인 3개 → `null`과 로그 · 3개 중 1개 → 행 2개 + `droppedForPrice: 1`.
6-1. 2단계 고정: 같은 시각의 로펙 표와 ① 후보 식별자 집합이 같고, ②에서 시세를 바꿔도(합성 시세 3벌) 표시 후보 집합과 `finalScore`가 변하지 않으며 `expectedCost`만
   바뀐다. 식별자 미발견은 `droppedForPrice`로 집계.
6-2. 시각·stale: 로펙 `isStale` 응답을 쓰면 `priceStale: true` · 시장 키를 하나도 안 쓴 결과(전부 fixed)는 `pricedAt: null` · `multi:` snapshotId는 최소 시각으로 파싱.
7. 시세 공유·재시도: 서로 다른 캐릭터 2명을 동시에 요청하면 겹치는 조회 묶음은 API 호출 1회 · 한 묶음을 인위적으로 실패시킨 뒤 다음 요청에서 그 묶음이
   재시도되고(실패 미캐시) 성공하면 5분 캐시에 들어감.

통합 검증(통합 책임자)
8. 디스코드: 임베드 설명 ≤ 4,096자, 필드 ≤ 1,024자, 상위 10개·반올림·`*` 표시(`fixed` 행은 `*` 없음)·0G 행 `무료 · —`·푸터 7항목의 조건부 표시(`pricedAt` null이면 시각
   생략, `priceStale`·`fixed`·`droppedForPrice` 문구)가 2절과 일치.
9. 카톡 미리보기/전체 보기 분리(고정 입력 4벌로 코어 없이 검증): 짧은 행 12개 → 미리보기 10개 + 링크, 전체 보기에 12개 · 짧은 행 8개 → 링크 없음, 전체 보기 미생성 ·
   **긴 행 8개(최종 메시지 > 1,500자)** → 본문 ≤ 1,500자 + 링크, 전체 보기 8개 · 긴 행 40개 → 본문 ≤ 1,500자 + 링크, 전체 보기 40개. `/스펙업`·`.스펙업`·`/ㅅㅍㅇ`·`.ㅅㅍㅇ` 네 입력 모두 동작, 접두사 없는 `ㅅㅍㅇ`은 침묵.
10. 실패·빈 결과 문구 3종(캐릭터 없음 → 코어 미호출 · 코어 `null` · `rows: []`), 카톡 예산 초과 경로.
11. 다른 커맨드 무영향: 팔찌·젬효율 결과와 소요 시간이 변경 전과 동일(진입점 탐색 확장) · `kakaoFull` 없는 기존 명령(`/도움말`·`/랭킹`)의 카톡 본문과 전체 보기가
    변경 전과 바이트 단위로 동일(브리지 훅 회귀).
12. 재등록 dry-run: 정의 88개, 이름 중복 없음.

배포 전제: `npm run register`(86 → 88개). 환경변수·서버 설정·폰 스크립트 변경 없음.

위험
- 로펙 배포마다 모듈 ID·청크 경로가 바뀐다 → 팔찌 때와 같이 소스 패턴 역추적, 실패하면 `null`과 로그. 스펙업 청크가 동적 로딩이라 탐색 범위가 넓다.
