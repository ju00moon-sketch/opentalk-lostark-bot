# 카톡 수요일 전체 공지 자동 알림

## 요청과 범위

카톡에도 로스트아크 공식 공지의 제목과 원문 링크를 자동으로 보낸다. 사용자 이미지와 추가 답변에 따라 한국 시간 수요일 당일 올라온 전체 공지(공지·상점·이벤트·점검)를 포함한다. 다른 날짜의 글은 제외하고 목요일 00:00에는 미발송분도 만료한다. 디스코드 발송 대상·화면과 양쪽 `/업데이트` 수동 조회는 유지한다. 공용 공식 API 조회에 실패하면 성공할 때까지 1분 간격으로 재시도하고, 정상 응답을 받으면 3분 주기로 돌아간다.

## 연결과 저장 계약

- 기존 공지 조회 결과를 카톡 피드에도 전달한다. 공식 API 예외·목록 형식 오류에만 1분 재시도를 적용하며 시도 횟수 제한은 없다. 정상적인 빈 목록이나 새 공지가 없는 경우, API 성공 후 저장·발송 처리 실패에는 기본 3분 주기를 유지한다. 진행 중 요청이 끝난 뒤 다음 주기를 예약해 요청이 겹치지 않는다. 카톡 저장 실패가 디스코드 발송을 막지 않는다.
- 첫 유효 조회에서도 수요일 당일 공지는 피드에 넣는다. API가 점검 중이었다가 복구된 경우에도 그날 공지를 놓치지 않게 한다. 다른 날짜의 글은 기준점 계산에만 쓰고 발송하지 않는다.
- 새 `kakao-update-notify.json`은 공지 기준점과 최대 100개 당일 이벤트를 원자적으로 저장한다. 잘못된 JSON·스키마는 저장과 피드 제공을 거부한다. 공식 URL과 게시 일시를 검증하며 무효·미래 공지는 처리하지 않는다.
- 제목·분류로 발송 대상을 제한하지 않는다. 게시 날짜는 실제 달력 날짜인지 확인한다. 항목 본문은 `[분류] 제목`과 원문 URL 두 줄이며 분류가 없으면 `공지`를 쓴다.
- `GET /bridge/updates/<기존 비밀 경로>`는 기존 인증 경로를 재사용한다. 응답은 `{ version: 1, ready, cursor, events: [{ id, text, expiresAt }] }`. 준비 전에는 `ready: false`; 오류는 503, 인증 불일치는 404, 캐시는 금지한다. 방·닉네임·기존 상태는 응답에 포함하지 않는다.
- 폰은 기존 `SERVER`에서 조회 URL을 유도하고 60초마다 확인한다. `ROOMS` 범위 안의 카톡 단체방 중 실제 알림을 받은 방만 기억한다. 1:1 대화는 자동 발송 대상에서 제외한다. 기존 명령 입력 필터는 유지한다.
- 각 방은 처음 준비된 피드를 볼 때 그날 이벤트가 있으면 모두 전달하고, 없으면 현재 기준점부터 시작한다. 준비 전 피드에서 복구한 경우도 같다. 아직 보내지 않은 공지를 번호순으로 묶되 헤더 `❕ 로스트아크 공지사항`과 빈 줄을 포함해 1,500자 이하로 나눈다. 각 묶음 안에서는 최신 번호를 위에 표시한다. 성공한 묶음의 최대 번호만 영속 저장하고 실패한 묶음부터 당일 재시도한다. 다른 방의 성공에는 영향을 주지 않는다. 재시작·재컴파일에서 정상 기록을 복원한다. 손상 기록은 임의 초기화하지 않는다.
- 폰 응답·주기 조회 동시성을 제어하고, 재컴파일 시 기존 타이머를 해제하며 진행 중 요청의 후속 전송도 중단한다. 저장 오류·인증 오류·통신 실패가 방에 반복 오류 메시지를 보내지 않도록 한다.

## 검증과 구현 순서

1. 임시 피드 테스트를 먼저 작성해 미구현 실패를 확인한다. 수요일 전체 공지·최초 복구·KST 자정·다른 요일·재시작·저장 실패·손상·만료와 API 연속 실패·성공 후 주기 복귀를 검증한다.
2. 폰 스크립트를 실행하는 격리 하네스에서 최초 당일 전달·1,500자 묶음·최신순·방 필터·중복 조회·묶음 부분 실패·재시작·정지·만료와 기존 명령을 검증한다.
3. 실제 HTTP 라우트에서 인증·준비·오류·공지 응답을 확인하고, 기존 디스코드 발송과 카톡 명령 조회를 회귀 검증한다. 실제 외부 자료는 조회만 하며 시험 메시지는 가짜 채널에 보낸다.
4. 도움말·README·홈페이지 사용법을 맞추고 작성하지 않은 검토자의 독립 검토를 받는다. 운영과 실기기 검증은 격리 검증과 구분한다.

## 운영 전제와 한계

- 서버 소스 배포와 폰 스크립트 교체가 둘 다 필요하다. `SERVER`·`ROOMS`는 기존 값을 유지한다. 신규 환경변수·의존성·명령 재등록은 없다. 상태 파일은 루트에 생성하며 저장소에 포함하지 않는다.
- 폰 켜짐·앱 실행·해당 방 알림 세션이 필요하다. 폰 재시작 뒤 세션이 없으면 방에 새 카톡 알림이 와야 전송할 수 있다. 동일한 방 제목은 구분할 수 없다.
- 자동 알림 중지는 `AUTO_UPDATES=false`로 변경한 뒤 재컴파일한다. 앱의 단순 off 스위치만으로 주기 조회가 중지된다고 보증하지 않는다. 같은 이름의 개인방·다른 앱 세션을 관측하면 해당 방의 자동 발송을 보류하고 실제 카톡 단체방 알림을 다시 받아야 재개한다.
- 카톡 전송 성공 직후 진행 번호를 저장하기 전에 프로세스가 종료되면 재전송될 수 있다. 카톡 수신 확인 기능이 없어 정확히 한 번 전달을 보증하지 않는다. 실패 여부는 앱의 전송 결과를 기준으로 판단한다.
- 폰 앱 데이터를 초기화하거나 재설치하면 방별 기록이 사라져, 다시 연결한 방은 해당 수요일 당일 공지를 한 번 더 받을 수 있다.
- 첫 설치·새 방 연결에서도 피드에 남은 해당 수요일 당일 공지를 보낸다. 이전 날짜 공지는 `/업데이트` 또는 `.업데이트`로 직접 확인할 수 있다. 링크 미리보기 카드의 표시 여부는 카톡 앱에서 결정한다.
- 이번 요청은 구현·검증 범위이며 실제 머지·배포·폰 적용 결과를 별도로 기록한다. 공개 출시 노트에는 출시 날짜를 표시하지 않는다.

## 검증 기록

- 작성자 검증 41개(피드 7·API 재시도 4·HTTP 연결 3·폰 27)와 별도 독립 검증 23개를 통과했다. 최초 당일 전달·연속 API 실패와 성공 복귀·묶음 부분 실패·재시작·손상 저장·자정 만료를 확인했다.
- 제품 담당자의 최종 교차 검토에서 새 독립 검증 21개가 통과했고 남은 P1/P2 결함은 없었다. 실자료 선별·첫 연결과 복구·API 실패 주기·묶음 부분 실패를 확인했으며, 기존 저장·인증·명령 회귀 검토 결과도 유지된다.
- 실제 공식 API 응답 73개에서 해당 수요일 공지 3개(업데이트·알려진 이슈·상점)를 선별했다. 실제 폰 스크립트를 격리 실행하여 제목·원문 링크를 271자 한 묶음으로 출력하고 다음 조회에서 중복 전송이 없음을 확인했다.
- 실제 명령 진입점과 카톡 `/업데이트`·`.업데이트`·`.업뎃`의 기존 출력, 디스코드·카톡 도움말을 확인했다. 명령 정의 58개·61개는 기존과 동일하고 도움말 필드 최대 길이는 912/1,024자다. 변경된 자바스크립트 5파일의 문법과 변경분 검사를 통과했다.
- 실제 휴대전화 컴파일·앱의 다중 스레드·배터리 정책·미리보기 카드·카톡 도착은 아직 확인하지 않았다. 검증 중 실제 방·채널에 시험 메시지를 보내거나 운영 상태를 변경하지 않았다. 서버 배포와 폰 적용도 수행하지 않았다.
